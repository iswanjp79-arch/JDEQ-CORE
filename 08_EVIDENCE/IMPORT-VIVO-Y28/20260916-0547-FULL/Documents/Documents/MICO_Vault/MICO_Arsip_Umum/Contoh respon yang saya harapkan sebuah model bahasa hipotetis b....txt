## 4) Workflow n8n
### Flow
```text
Manual Trigger
↓
Read registry.json
↓
Parse JSON
↓
Filter Accepted ADRs
↓
Select ADR relevan
↓
Send ke AI Agent / next workflow
↓
Log hasil
↓
Update registry jika ada ADR baru
```
### Node ringkas
- **Manual Trigger**: memulai workflow.
- **Read File / HTTP Request**: baca `registry.json`.
- **Code Node**: parse dan normalisasi data.
- **Switch / IF**: pilih ADR aktif.
- **Set Node**: ringkas output.
- **AI Agent Node**: gunakan ADR sebagai konteks.
- **Write File / Log Node**: simpan hasil audit.

## Fungsi tiap lapisan
### 1. Input Gate
Lapisan ini memeriksa apakah input layak diproses, misalnya apakah ada prompt injection, konflik instruksi, atau payload yang terlalu liar. Tujuannya supaya data mentah tidak langsung masuk ke agen. [4][5][1]
### 2. SSOT Prompt Gate
Di sini n8n mengambil prompt inti dari SSOT, bukan dari teks acak di node. Ini menjaga role, batas, format output, dan prioritas instruksi tetap stabil. [6][7][8]
### 3. Tool / Permission Gate
Lapisan ini menentukan tool mana yang boleh dipakai agen. Pada n8n, best practice-nya memang mengelola tool dan sub-workflow secara jelas supaya agent tidak punya akses berlebihan. [9][10][2]
### 4. Execution Gate
Sebelum tindakan nyata, workflow memutuskan apakah hasil cukup aman untuk dieksekusi atau perlu simulasi/konfirmasi manusia. Ini penting untuk operasi file, web, sistem Android, dan API sensitif. [2][11][12]
### 5. Audit / Log Gate
Semua hasil dicatat, dipantau, dan jika perlu dimirror ke SSOT atau storage lain. Lapisan ini membuat workflow bisa di-review dan di-rollback bila ada anomali. [13][14][1]
## Contoh node n8n
- **Webhook / Chat Trigger**: menerima input.
- **IF / Switch Node**: input aman atau tidak.
- **Read File / HTTP Request**: ambil SSOT prompt.
- **AI Agent Node**: proses tugas dengan prompt dan tool.
- **Execute Workflow / Sub-workflow**: tool terpisah untuk tugas tertentu.
- **Code Node / Write Node**: validasi dan simpan hasil.
- **Google Drive / GitHub / DB Node**: mirror dan arsip.

Bagaimana cara sinkronisasi ADR ini agar dipahami semua agen
Cara sinkronisasi ADR agar dipahami semua agen adalah: **satu ADR harus disimpan di satu tempat resmi, lalu semua agen membaca versi yang sama dari registry itu, bukan salinan bebas**. ADR yang sudah diterima juga sebaiknya dianggap immutable; kalau ada perubahan, buat ADR baru dan tandai ADR lama sebagai superseded. [1][2][3]
## Pola sinkronisasi
- **Single source registry**: satu folder `DECISION_REGISTRY/` sebagai rujukan utama.
- **Version control**: simpan ADR di repo atau storage yang terverifikasi.
- **Immutable after accept**: ADR yang sudah accepted tidak diedit sembarangan.
- **Supersede, jangan overwrite**: keputusan baru selalu masuk sebagai ADR baru.
- **Index wajib**: semua agen mengacu ke `index.md` sebagai peta keputusan. [1][2][4]
## Alur sinkronisasi antar agen
```text
User / DOLA
   ↓
ADR Draft
   ↓
Review & Accept
   ↓
ADR Registry (SSOT)
   ↓
n8n sync/read step
   ↓
Semua agen baca versi yang sama
   ↓
Jika ada perubahan → buat ADR baru
```
## Cara supaya semua agen paham
### 1. Jadikan ADR sebagai data, bukan obrolan
Setiap agen harus membaca ADR dari file, bukan mengandalkan ingatan percakapan. Ini mencegah perbedaan interpretasi antar model. [2][1]
### 2. Pakai index yang selalu diperbarui
`index.md` atau `registry.json` berisi daftar ADR aktif, status, tanggal, dan link ke file. Jadi DOLA, MICO, n8n, dan agen lain selalu masuk ke sumber yang sama. [3][4][2]
### 3. Tambahkan status yang jelas
Minimal:
- Proposed.
- Accepted.
- Rejected.
- Superseded.  
Status ini membantu agen lain tahu apakah keputusan sudah final atau masih draft. [2][1]
### 4. Sinkronkan lewat workflow otomatis
n8n bisa memantau folder ADR, lalu:
- membaca file baru,
- memperbarui index,
- mengirim notifikasi ke agen,
- menyebarkan perubahan ke mirror cloud.  
Ini cocok dengan pola sinkron dokumen/workflow yang memang umum di n8n. [5][6]
### 5. Pakai ringkasan kanonik
Selain file ADR lengkap, buat `ADR-SUMMARY.md` atau `canonical_registry.json` agar agen cepat memahami keputusan inti tanpa membaca semua sejarah. [7][2]
## Praktik terbaik
- Jangan edit ADR accepted langsung.
- Jangan biarkan beberapa versi aktif dengan nama berbeda.
- Jangan biarkan agen menyimpan copy sendiri sebagai kebenaran.
- Setiap agen harus menyebutkan ID ADR saat merujuk keputusan.
- Kalau ada konflik, registry yang menang, bukan chat terakhir. [1][2][3]

Dengan model ini, semua agen MICO akan mengacu pada keputusan yang sama dan tidak membangun versi arsitektur yang saling bertabrakan.

## Field yang disarankan
- **id**: identitas ADR unik.
- **title**: judul singkat.
- **status**: Proposed, Accepted, Rejected, Superseded.
- **date**: tanggal keputusan.
- **owner**: agen/role penanggung jawab.
- **scope**: area sistem yang terdampak.
- **file**: path file ADR Markdown.
- **summary**: ringkasan satu kalimat.

## Cara dipakai di n8n
Alur praktisnya:
1. **Read File / HTTP Request** baca `registry.json`.
2. **Parse JSON** jadi object.
3. **IF / Switch** cek status ADR yang relevan.
4. **Set / Code Node** pilih ADR aktif.
5. **AI Agent Node** pakai ADR yang terpilih sebagai context.
6. **Write File** jika ada ADR baru.
7. **Update registry.json** setiap kali ada perubahan status. [1][2][5]
## Aturan penting
- Jangan simpan dua ADR aktif yang saling bertentangan.
- Jika ada keputusan baru, update registry dengan status baru, jangan edit diam-diam ADR lama.
- Jangan hilangkan field `status`, `file`, dan `scope`.
- Simpan versi cadangan registry sebelum update besar. [4][6][7]
