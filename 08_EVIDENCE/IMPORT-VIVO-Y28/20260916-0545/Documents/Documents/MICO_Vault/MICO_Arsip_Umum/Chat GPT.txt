## Mengapa ini lebih kuat
Capability-oriented architecture memisahkan “apa yang sistem bisa lakukan” dari “di mana ia berjalan”, dan itu membuat migrasi host, failover, serta perluasan sistem jauh lebih mudah. Pola registry juga mendukung discovery, constraint, versioning, dan dependency tracking secara terstruktur. [1][2][4]
## Yang perlu dipertahankan
- **Capability Registry** harus menjadi SSOT utama.  
- **Node Registry** tetap perlu, tetapi hanya sebagai pemetaan host aktif.  
- **Contract, Policy, Evidence, Identity, Lifecycle** harus berada di lapisan enterprise fabric.  
- Host fisik hanya menjalankan capability yang diizinkan oleh registry dan kontrak. [1][5][3]
## Perbaikan penting
- “Vivo = Gateway” sebaiknya diubah menjadi **Gateway Fabric berjalan di Vivo**.  
- “Z83 = dispatcher” sebaiknya diubah menjadi **Core Orchestration Fabric berjalan di Z83**.  
- “PC i5 = AI” sebaiknya diubah menjadi **Compute Fabric menjalankan AI Executor**.  
- Dengan begitu, perangkat tidak menjadi identitas; perangkat hanya menjadi lokasi eksekusi.

- **SSOT Fabric**
Itu konsisten dengan pola registry enterprise yang memerlukan identitas, owner, domain, interface, version, policy, dependency, dan constraints pada setiap capability. [1][2]
## Keputusan arsitektur
Saya menilai perubahan ini sebagai **APPROVED WITH CONDITIONS**. Syaratnya adalah:
- Capability Registry harus dijadikan SSOT utama.
- Node Registry hanya menjadi pemetaan host.
- Semua capability harus punya owner, contract, policy, runtime characteristic, dan evidence trail.
- Perubahan host harus cukup mengubah registry, bukan desain sistem. [1][5][6]
## Kalimat final yang paling tepat
**MICO-JDEQ bukan kumpulan perangkat; MICO-JDEQ adalah kumpulan capability yang dibungkus oleh host.** Itu lebih tahan lama, lebih mudah diaudit, dan lebih mudah dipindahkan saat hardware berubah. [1][3]

Rancang node registry untuk pemetaan host aktif
Berikut rancangan **Node Registry** untuk pemetaan **host aktif** yang cocok dengan MICO-JDEQ. Registry ini harus jadi SSOT untuk **host yang sedang hidup**, sementara capability tetap menjadi lapisan utama. [1][2][3]
## Tujuan registry
Node Registry dipakai untuk menjawab pertanyaan praktis: host mana yang aktif, capability apa yang sedang berjalan di host itu, status kesehatannya bagaimana, dan kontrak apa yang mengikatnya. Pola seperti ini umum pada registry enterprise: ada identity, owner, version, runtime characteristics, relationships, policy, availability, dan confidence. [4][5]
## Prinsip desain
- **Host-only scope.** Registry ini tidak menyimpan logika capability penuh, hanya pemetaan host aktif dan statusnya.
- **SSOT untuk host state.** Jika status host berubah, update hanya lewat event atau record baru, bukan edit diam-diam.
- **Append-only evidence.** Setiap perubahan penting harus punya jejak audit.
- **Capability-aware.** Setiap host harus menunjuk capability yang sedang di-*bind* ke sana.
- **Fail-safe.** Jika host tidak heartbeat, status harus turun otomatis. [6][7][8][4]
## Entitas inti
### 1. Node
Representasi satu host fisik atau logis yang aktif.
### 2. Host Binding
Relasi antara node dan capability yang sedang berjalan di host tersebut.
### 3. Runtime Snapshot
Kondisi ringkas host saat terakhir dicek: RAM, storage, suhu, CPU load, network, battery, dan uptime.
### 4. Health State
Status operasional host: `ACTIVE`, `DEGRADED`, `SUSPECT`, `DOWN`, `MAINTENANCE`, `RETIRED`.
### 5. Evidence Link
Pointer ke bukti append-only untuk setiap perubahan state. [9][10]
## Skema minimal
### `node_id`
ID unik host.
### `node_name`
Nama manusia, misalnya `VIVO_Y28`, `Z83`, `INFINIX`, `TRAVELMATE`, `PC_I5`.
### `node_type`
`mobile`, `server`, `laptop`, `pc`, `backup`.
### `host_role`
Peran eksekusi saat ini, misalnya `Gateway Host`, `Telemetry Host`, `Core Orchestration Host`.
### `status`
`ACTIVE`, `DEGRADED`, `SUSPECT`, `DOWN`, `MAINTENANCE`, `RETIRED`.
### `capabilities_bound`
Daftar capability yang sedang dipetakan ke host.
### `last_heartbeat`
Waktu heartbeat terakhir yang valid.
### `last_health_check`
Waktu health check terakhir.
### `resource_budget`
RAM, storage, CPU, battery, thermal headroom.
### `network_quality`
Status koneksi, latency, jitter, offline/online.
### `owner`
Pemilik administratif.
### `policy_ref`
Policy atau kontrak yang mengizinkan host ini beroperasi.
### `version`
Versi record node.
### `evidence_ref`
Hash atau pointer ke bukti audit. [7][8][9]

## Aturan pemetaan host aktif
- Satu node boleh memegang lebih dari satu capability kalau resource budget cukup.
- Satu capability punya satu host aktif utama, bisa punya host cadangan.
- Jika heartbeat gagal melewati threshold, status turun dari `ACTIVE` ke `SUSPECT`, lalu `DOWN`.
- Pergantian host tidak mengubah capability definition, hanya binding-nya.
- Node yang retired tidak boleh menerima binding baru. [4][11][12]
## Event yang wajib dicatat
- `NODE_REGISTERED`
- `NODE_HEARTBEAT`
- `NODE_HEALTH_CHANGED`
- `NODE_CAPABILITY_BOUND`
- `NODE_CAPABILITY_UNBOUND`
- `NODE_POLICY_CHANGED`
- `NODE_RETIRED`
Setiap event sebaiknya append-only dan tamper-evident dengan hash chain atau log yang tidak bisa diubah sembunyi-sembunyi. [6][7][8]
## API minimal
### `GET /nodes`
Daftar semua node aktif dan statusnya.
### `GET /nodes/{node_id}`
Detail satu node.
### `POST /nodes/register`
Daftarkan host baru.
### `POST /nodes/{node_id}/heartbeat`
Update heartbeat.
### `POST /nodes/{node_id}/health`
Kirim hasil health check.
### `POST /nodes/{node_id}/bind`
Bind capability ke host.
### `POST /nodes/{node_id}/unbind`
Lepas capability dari host.
### `POST /nodes/{node_id}/retire`
Tandai host pensiun.
## ADR singkat
**ADR-Node-001 — Host Mapping Registry**  
**Status:** APPROVED WITH CONDITIONS.  
**Decision:** Node Registry hanya menyimpan pemetaan host aktif, status kesehatan, dan binding capability; capability definition tetap berada di Capability Registry.  
**Alasan:** Memisahkan identitas host dari kemampuan sistem, memudahkan migrasi perangkat, dan mengurangi coupling.  
**Konsekuensi:** Pergantian host cukup update binding, bukan redesign. [4][5][13]
