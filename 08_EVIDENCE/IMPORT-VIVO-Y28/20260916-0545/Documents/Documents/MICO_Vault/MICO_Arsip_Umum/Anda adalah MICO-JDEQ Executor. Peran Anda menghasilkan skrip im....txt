KONTEKS ARSITEKTUR (WAJIB DIIMPLEMENTASIKAN):
- Layer -1: Governance (doktrin.json, aturan hak akses)
- Layer 0: SSOT (TinyDB + NetworkX graph, schema fakta standar)
- Layer 1: Reality Engine (ingestion fakta dari file JSON)
- Layer 2: Context Compiler (membangun konteks misi dari SSOT)
- Layer 3: Planner (dynamic planning berdasarkan konteks, bukan hard-coded)
- Layer 4: Agent Router (pemilihan model berdasarkan capability + cost + reliability)
- Layer 5: Execution Kernel (dry-run + eksekusi aman, integrasi llama.cpp CLI untuk model lokal)
- Layer 6: Verification (DOLA scoring matrix)
- Layer 7: Reflection + Learning (loop tertutup yang mengupdate SSOT)

PLANNER HARUS:
- Membaca konteks dari Context Compiler.
- Mencari pola sukses di SSOT berdasarkan misi serupa.
- Menghasilkan langkah-langkah adaptif (bukan hard-coded).
- Menyimpan hasil perencanaan ke SSOT.
AGENT ROUTER HARUS:
- Memiliki registry model minimal (local_llama, chatgpt, gemini, deepseek).
- Memilih model berdasarkan: reliability, cost, specialties, dan required_reliability.
- Fallback berantai jika model pertama gagal.
- Mencatat performa ke log untuk pembelajaran.
EXECUTION KERNEL HARUS:
- Wajib dry-run sebelum eksekusi.
- Hanya menjalankan tindakan yang terdaftar di whitelist.
- Untuk tugas reasoning, memanggil llama.cpp via subprocess (jika tersedia) atau memberikan instruksi mock yang jelas.
DOLA (VERIFICATION) HARUS:
- Menerima hasil eksekusi.
- Menghasilkan skor: consistency, risk, cost, performance, security.
- Jika skor di bawah threshold, memicu review.
REFLECTION + LEARNING HARUS:
- Menerima hasil DOLA.
- Menyimpan lessons learned ke SSOT.
- Mengupdate Planner history dengan success rate.
- Loop tertutup: hasil pembelajaran mempengaruhi perencanaan berikutnya.

Audit Planner
Status: PARTIAL VERIFIED
Yang sudah terbukti (VERIFIED)
Model GGUF tidak bermasalah. Bukti Anda sudah kuat: test_mico.py mengirim system message melalui API.
Model menjawab sebagai MICO-JDEQ.
Artinya model mampu mengikuti identitas yang diberikan.
llama-server hidup. Endpoint /health mengembalikan status":"ok". 
PocketPal selalu menampilkan "Saya Qwen". Ini konsisten dengan tidak adanya system prompt yang efektif pada permintaan yang dikirim PocketPal. 
Yang belum bisa dipastikan
Kalimat berikut:
flag -sp pada llama-server tidak diterjemahkan menjadi system prompt untuk endpoint /v1/chat/completions
Belum tentu benar.
Ada beberapa kemungkinan:
Kemungkinan A (paling mungkin)
PocketPal mengirim request sendiri.
Misalnya:
{ "messages":[ { "role":"user", "content":"Halo" } ] } 
Server menerima request tersebut apa adanya.
Kemungkinan B
Versi llama-server yang Anda pakai memang tidak menerapkan -sp ke endpoint OpenAI API.
Ini tergantung versi llama.cpp.
Kemungkinan C
PocketPal sendiri mengirim system prompt bawaan.
Misalnya:
You are Qwen... 
Kalau begitu prompt global Anda akan tertimpa.
Menurut saya, solusi terbaik bukan mengubah model.
Saya juga tidak menyarankan mengubah GGUF.
Solusi Arsitektur
Saya memilih opsi nomor 2 dari surat Human Authority.
PocketPal ↓ MICO Proxy ↓ llama-server ↓ Qwen 
Proxy bertugas:
menerima request PocketPal 
mengecek apakah ada system message 
jika tidak ada 
menambahkan:
{ "role":"system", "content":"Kamu adalah MICO-JDEQ ..." } 
baru meneruskan ke
127.0.0.1:8080 
Kenapa proxy?
Karena:
tidak menyentuh model
tidak mengubah GGUF
tidak bergantung fitur PocketPal
tidak bergantung implementasi -sp
bisa dimatikan kapan saja
Secara arsitektur ini paling bersih.
Yang saya lakukan pertama
Sebelum menulis satu baris kode pun saya ingin memastikan satu fakta.
Saya akan meminta DeepSeek Executor menjalankan satu eksperimen.
curl /v1/chat/completions 
dua kali.
Request 1
Tanpa system.
Request 2
Dengan system.
Kalau hasilnya:
Request1 ↓ Saya Qwen Request2 ↓ Saya MICO 
Maka penyebabnya 100% berada di sisi request, bukan di model dan bukan di GGUF.
